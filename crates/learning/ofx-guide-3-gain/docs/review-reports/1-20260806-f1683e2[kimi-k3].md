# Review: `ofx-guide-3-gain`

Overall: the crate **compiles cleanly** (`cargo check` is warning-free;
crate-local clippy reports only a style-level `doc_overindented_list_items`
warning on the crate-docs TODO at `src/lib.rs:4` and a `too_many_arguments`
(11/7) lint on `pixel_processing` at `src/processing.rs:11`). It is a
**faithful port** of the OFX guide's Example 3 "Gain"
(`Documentation/sources/Guide/Code/Example3/gain.cpp` in the vendored openfx
tree), extended with the parameter machinery the example exists to
demonstrate: `paramDefine` in `DescribeInContext`, cached param handles in
instance data, and `paramGetValueAtTime` at render and identity-check time.

It also absorbs the fixes from the guide-2 review:

- **Both images are fetched via `clip_get_image_managed`**
  (`src/lib.rs:372–373`), so `clipReleaseImage` runs on all paths including
  error paths — the guide-2 review's #1 (output-image leak on a failed source
  fetch) cannot recur.
- **No panic sites across the FFI boundary** — no `unwrap`/`expect`/`panic!`/
  `assert!` anywhere in `src/`; mutex poisoning and null pointers map to error
  codes.
- Abort-on-render returns `Ok(())` (`src/processing.rs:61`), not guide-2's
  `Err(kOfxStatOK)` sentinel.
- Pixel-offset arithmetic is `isize` throughout
  (`src/processing.rs:124–128`) — the guide-2 `c_int` overflow nit is gone.

Issues below are ranked by severity.

---

## 1. `IsIdentity` treats every gain ≤ 1.0 as identity — missing `.abs()` (most important)

`src/lib.rs:332`:

```rust
if gain - 1.0 < 0.000000001 {
```

The reference is `fabs(gain - 1.0) < 0.000000001` (`gain.cpp:577`); the
absolute value was lost in porting. As written, the condition holds for **any
gain below 1.0 + ε** — e.g. `0.5` (`-0.5 < 1e-9`) or `0.0` (`-1.0 < 1e-9`).
When the host honors `IsIdentity`, it bypasses the effect and renders the
`Source` clip directly, so gain `0.0` — which should produce a black frame —
passes the image through unchanged. Any gain in `[0, 1)` is silently a no-op
in hosts that query this action.

Unlike the guide-2 findings, this is a **regression introduced by the port**;
the C++ original is correct here.

**Fix:** `if (gain - 1.0).abs() < 0.000000001 {`.

## 2. `kOfxParamPropDisplayMax` is 1.0, the guide uses 10.0

`src/lib.rs:244`:

```rust
param_props.prop_set_double(kOfxParamPropDisplayMax, 0, 1.0)?;
```

The reference sets the display max to `10.0` (`gain.cpp:268–271`), and the
guide text leans on it ("a slider would only allow values between 0.0 and
10.0 for our gain param, but the parameter could be set to a million via
other means"). Since this crate's stated purpose is to follow the guide, the
`1.0` looks like a typo rather than a deliberate choice. Impact is limited to
the host's slider range — the value itself is correctly unclamped above
(`kOfxParamPropMax` is unset, matching the reference) — so hosts still accept
any typed/animated value.

**Fix:** set the display max to `10.0` (or record the deviation as
deliberate).

## 3. Dead `Sub` trait bound on `pixel_processing`

`src/processing.rs:25`:

```rust
T: std::ops::Sub<Output = T> + Copy + Default,
```

Nothing in the gain pixel loop subtracts `T` — the bound was only needed by
invert's `max - *src_pix` and survived the copy-paste. Harmless for the three
concrete types used, but it misstates the function's requirements.

**Fix:** drop the bound to `T: Copy + Default`.

## 4. Minor nits

- **Const-correctness**: instance data is fetched as
  `&*(my_data_ptr as *mut MyInstanceData)` (`src/lib.rs:324,366`) and
  `pixel_address` returns `*mut T` even for the read-only source
  (`src/processing.rs:112–131`). `*const` would better express intent in
  both places; no behavioral difference.
- **Clippy, crate-local**: doc-overindent on the crate-docs TODO
  (`src/lib.rs:4`); `too_many_arguments` (11/7) on `pixel_processing`
  (`src/processing.rs:11`) — the conversion-fn trio (`from_f64`, `into_f64`,
  `max`) would bundle naturally into a small struct if this ever grows.
- **Clippy, workspace-wide**: a full `cargo clippy` currently fails inside
  `openfx-bindings` with 17 `not_unsafe_ptr_arg_deref` hard errors (helper
  fns dereferencing host pointers without being `unsafe fn`). Pre-existing
  and out of scope for this crate — guide-2's report saw only a
  `missing_safety_doc` warning there, so this is the newer nightly toolchain
  turning the lint into an error — but it does block linting any dependent
  crate until addressed.
- **`tracing::error!` in `set_host` is still a silent no-op** — the
  crate-docs TODO about initializing a tracing subscriber remains open
  (`src/lib.rs:1–5,108–113`), inherited unchanged from guides 1 and 2.

## 5. Still present from earlier reviews (declined there; listed for completeness)

- **Plugin identifier vs icon filename**: `pluginIdentifier` is
  `c"org.openeffects:GainExamplePlugin"` (colon — faithful to the guide,
  `src/lib.rs:54`), but the bundled icon is
  `org.openeffects.GainExamplePlugin.png` (dot —
  `xtask/src/learning_ofx_guide_3_build_plugin.rs:18`). The OFX packaging
  spec requires the icon to be named `pluginIdentifier + ".png"`, so hosts
  implementing the convention will never find it. Same status as in guides 1
  and 2.

## 6. Things verified as correct (no action needed)

- `Describe` matches the guide: label, grouping, filter-only context,
  float/short/byte depths, `kOfxImageEffectRenderFullySafe`, host frame
  threading = 1 (`src/lib.rs:171–200`).
- `DescribeInContext`: rejects non-filter contexts with
  `kOfxStatErrUnsupported` (`src/lib.rs:214–217`); Output and Source clips
  each with RGBA/Alpha/RGB (`src/lib.rs:219–233`); the `gain` param with
  `kOfxParamDoubleTypeScale`, default 1.0, min 0.0, display min 0.0, label
  and hint (`src/lib.rs:237–247`), and the `applyToAlpha` bool with default
  0, label and hint (`src/lib.rs:249–260`) — all matching `gain.cpp:240–300`
  except the display max in issue #2.
- Instance data lifecycle: `Box::into_raw` in `CreateInstance` /
  `Box::from_raw` in `DestroyInstance`, caching both clip handles and both
  param handles exactly as the C++ `MyInstanceData` does
  (`src/lib.rs:265–306`).
- `IsIdentity` protocol itself is right: fetches `gain` at the time from
  inArgs, sets `kOfxPropName` to `Source`, returns `kOfxStatOK` /
  `kOfxStatReplyDefault` (`src/lib.rs:308–338`) — only the comparison in
  issue #1 is wrong.
- Render loop fidelity: components → `n_comps` dispatch, pixel depth →
  (u8/255, u16/65535, f32/1.0) (`src/lib.rs:388–437`); clamping skipped for
  float via `(into_f64)(max) != 1.0`, preserving the C++ `MAX != 1`
  semantics (`src/processing.rs:85–87`); alpha pass-through via
  `i != 3 || apply_to_alpha` (`src/processing.rs:83`); black fill for
  out-of-bounds source pixels (`src/processing.rs:96–103`); abort polled
  every 20 rows (`src/processing.rs:54`); destination addressed once per row
  and incremented, sound under the spec guarantee that output bounds ⊇
  render window, with the impossible out-of-bounds case returning
  `kOfxStatFailed` rather than being silently skipped
  (`src/processing.rs:64–73`).
- Using the output image's component count and depth for both images is
  sanctioned by the guide (defaults guarantee source and output match when
  no clip-preferences action is trapped).
- `Cargo.toml` (`cdylib`, workspace inheritance), `justfile`, xtask wiring,
  and `.gitignore` hygiene (`/build/`) — all consistent with the sibling
  crates.

---

**Bottom line:** a faithful, well-hardened port of the guide's third
example, with the guide-2 review lessons applied. The one thing that must be
fixed is the **missing `.abs()` in `IsIdentity`** (#1) — it inverts the
feature's behavior for the entire `[0, 1)` gain range. #2 and #3 are
one-line fidelity/cleanup wins.
