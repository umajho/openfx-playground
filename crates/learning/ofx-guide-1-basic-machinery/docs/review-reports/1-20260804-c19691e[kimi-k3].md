# Review: `ofx-guide-1-basic-machinery`

Overall: the crate **compiles cleanly with no warnings** (crate-local clippy is clean
too), and it is a **faithful, spec-accurate port** of the OFX guide's "Basic
Machinery" example. The core lifecycle mechanics are correct:

- `set_host` only stores pointers and calls no OFX functions (mandated by the spec).
- Suites are fetched in `kOfxActionLoad`, the correct place.
- Action dispatch, `Describe`/`DescribeInContext`, the instance-data `Box`
  round-trip (`into_raw` → `from_raw`), and `IsIdentity` semantics (set
  `kOfxPropName` to `Source`, return `kOfxStatOK`) all match the spec.
- Edition-2024 idioms (`#[unsafe(no_mangle)]`, `c"..."` literals) are used
  correctly, and the `main_entry` signature matches `OfxPluginEntryPoint` exactly.

Issues below are ranked by severity.

---

## 1. Panics across the FFI boundary will abort the host process (most important)

`main_entry` and `set_host` are `extern "C"`. Inside their call trees there are
many panic sites:

- `set_host`: three `.expect()`s + `panic!` on double-init (`src/lib.rs:62–82`)
- every action: `Mutex::lock().expect("...poisoned")`
- `action_destroy_instance`: `assert!(!my_string.is_null(), ...)` (`src/lib.rs:353`)

Since Rust 1.71, a panic unwinding out of an `extern "C"` fn is a **process
abort** — so a poisoned mutex or a quirky host takes down the entire video
editor, not just this plugin. For a plugin loaded into a third-party process
this is the worst failure mode.

**Fix:** wrap the dispatch in `main_entry` with `std::panic::catch_unwind` and
map a caught panic to `kOfxStatErrFatal`/`kOfxStatFailed`; replace
`assert!`/`expect` with error-code returns where practical.

## 2. Plugin identifier / icon filename mismatch (spec violation)

- `pluginIdentifier` is `c"org.openeffects:BasicExamplePlugin"` (colon,
  `src/lib.rs:35`)
- the bundled icon is `Resources/org.openeffects.BasicExamplePlugin.png` (dot,
  produced by the xtask)

The OFX packaging spec states: *"The icon file must be named as the
corresponding `pluginIdentifier` field from the `OfxPlugin`, postpended with
'.png'"*. As written, hosts that implement this convention (e.g. Resolve
thumbnails) will never find the icon. Also, the spec's own guidance for
identifiers is reverse-domain **dot** notation, and `:` in filenames is
pathological on macOS (Finder displays it as `/`). The sibling `ntsc-openfx`
crate repeats the same colon/dot inconsistency, so if this is a deliberate house
style, the icon naming needs to follow the identifier — but the simpler fix is
a dot in the identifier.

(Related, in the xtask rather than this crate: the OFX spec also lists
`CFBundleExecutable` as a required `Info.plist` key; it's currently omitted.)

## 3. `set_host` is hostile to reload cycles

`HOST_STRUCT` is a `OnceLock` that panics if `setHost` is called twice.
`action_unload` clears `SHARED_DATA` but `HOST_STRUCT` can never be reset. If a
host re-scans/reloads the plugin while keeping the dylib mapped (hosts do cache
and re-query), the second `setHost` aborts the process (compounding issue #1).
Tolerating re-initialization (or silently accepting an identical re-set) is
safer and spec-compatible.

## 4. Missing null check on `action`

`CStr::from_ptr(action)` (`src/lib.rs:92`) on a null pointer is UB. The spec
guarantees non-null, so this is defensive, but a one-line check returning
`kOfxStatErrBadHandle` costs nothing in an FFI entry point that already can't
trust the host fully.

## 5. Soundness/style nits

- **`&'static` laundering of host-owned pointers** (`SaferHostStruct<'static>`,
  suites in `SharedData`): the spec does guarantee these pointers stay valid
  while the plugin is loaded, so this works — but storing the raw
  `OfxPropertySetHandle`/`*const OfxPropertySuiteV1` instead of Rust references
  would (a) avoid asserting immutability of host-owned memory and (b) eliminate
  the need for the `SaferHostStruct` wrapper entirely. In practice it's mostly
  theoretical here (`OfxPropertySetStruct` is opaque/ZST, suites are only read).
- **Dead state**: `SharedData.host_struct` is stored but `#[expect(unused)]` —
  it's a clone of what's already in `HOST_STRUCT`. Pick one source of truth; in
  a learning crate the redundancy is confusing.
- **Error-code consistency**: missing suite function pointers return
  `kOfxStatFailed` in most actions, but `action_load` uses the more precise
  `kOfxStatErrMissingHostFeature` for the analogous null-suite case. Use the
  latter everywhere.
- **`match true { _ if ... }` dispatch** (`src/lib.rs:94`): works, but a plain
  `if / else if` chain is the idiomatic spelling and reads better.
- The acknowledged `FIXME` leak in `action_create_instance` (`src/lib.rs:317`)
  is trivially fixable by reconstructing the `Box` on the error path.
- Trivial: `action_describe_action` has a stuttered name (`action_describe`
  suffices).

## 6. Things verified as correct (no action needed)

- `OfxGetPlugin` returning `*const OfxPlugin` vs the header's `OfxPlugin*` —
  ABI-identical, and `*const` is better Rust.
- `&*EFFECT_PLUGIN_STRUCT` from a `LazyLock` — stable address, forced init; fine.
- `kOfxStatErrUnsupported` for a non-filter context in `DescribeInContext`,
  unknown actions → `kOfxStatReplyDefault` — both spec-correct.
- `Cargo.toml`: `cdylib`, workspace inheritance, lints — all fine.
  `.gitignore`/`build/` hygiene is fine (root `.gitignore` covers `.DS_Store`;
  build artifacts aren't tracked).

---

**Bottom line:** mechanically correct learning crate; the two things worth
fixing before anything ships are the **panic-across-FFI** behavior (#1) and the
**identifier/icon mismatch** (#2).
